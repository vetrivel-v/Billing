# ADR-0029: Windows packaging, the private local database and the installed runtime

- Status: Accepted and implemented in the Windows packaging milestone (after Task 1.18). R-040 stays open; packaging does not enable production billing.
- Date: 2026-10-23
- Builds on: ADR-0006 (Electron security baseline), ADR-0013 (renderer origin and launch secret), ADR-0027 (backup format and verified recovery), ADR-0028 (end-to-end harness)

## Context

Until now CommerceBill ran from a developer checkout: Node, npm, a developer-started PostgreSQL (`db:start`) and environment variables. The target is one non-technical person on one Windows laptop, offline, with no Docker, no cloud and no command line.

## Decisions

1. **One installer, per-user, no elevation.** `CommerceBill-Setup-<version>.exe` is an NSIS installer built by electron-builder (`npm run package:win`). It installs for the current Windows user (default `%LOCALAPPDATA%\Programs\CommerceBill`), needs no administrator rights, creates a Start-menu and a desktop shortcut that start `CommerceBill.exe` directly (no console, no script), and registers a per-user uninstall entry. The installation folder is replaceable program files only.
2. **A private PostgreSQL, never SQLite.** The installer carries the PostgreSQL 18 Windows binaries already used in development (`@embedded-postgres/windows-x64`; R-030 records that this build line is a beta). The application initialises a cluster on first launch and starts and stops `postgres.exe` itself. It listens on **127.0.0.1 only** (`listen_addresses=127.0.0.1`, random free loopback port recorded in `runtime.json`), so no firewall rule is created or needed. Authentication is `scram-sha-256` with a generated password. The Fastify service also listens on 127.0.0.1 only.
3. **Data lives outside the program.** All mutable state is under `%LOCALAPPDATA%\CommerceBill` (override for tests: `COMMERCEBILL_DATA_DIR`, absolute, local drive): `data\pg` (the database), `config\` (runtime.json, secrets.bin, runtime-status.json), `logs\`, `backups\` (and `backups\pre-upgrade\`), `tmp\`. Upgrade, uninstall and reinstall never touch it; uninstall says so in plain words. A reinstall finds the cluster, recognises it by the stored cluster identity and does not run setup again.
4. **Generated credentials, protected by Windows.** The database password (and the safety-backup passphrase, decision 7) are generated with a CSPRNG on first launch and stored in `secrets.bin`, encrypted with Electron `safeStorage` (Windows DPAPI, bound to this Windows user on this computer). They are passed only to the main process and the service it starts, never to the renderer, never in a bundle or source file, and never written to a log (the logger redacts connection strings and known secret values). Consequence: copying the data folder to another computer or Windows account does not carry a usable password. Recovery is by restoring a backup (R-110).
5. **Start-up, in order.** Single-instance lock; splash window; resolve paths; load secrets; decide **fresh / existing / broken** from what is on disk (decision matrix in `runtime/startup.ts`); start PostgreSQL (reuse a still-running one from `postmaster.pid`, clean up a stale pid file); pre-upgrade backup and migrations if the schema is older (decision 7); start the service; open the window. **A missing or unreadable cluster is never silently replaced by a new empty one**: if `config\runtime.json` says a database existed but `data\pg` is missing, or the credentials cannot be read, start-up stops with a plain-language dialog (Try again, Save diagnostics, Open log folder, Quit). A new empty database is created only when nothing at all exists.
6. **Shutdown.** Closing the last window stops the service, then PostgreSQL with `pg_ctl stop -m fast` (a clean shutdown; the log must say "database system is shut down"), then exits. If the main process is killed, the service watches its parent process id and exits by itself, and the next launch finds and reuses or cleans up the database (verified by test).
7. **Pre-upgrade verified backup.** When the installed schema is older than the one the new version needs and the database holds a business, the application first writes a safety backup using the Task 1.17 archive (AES-256-GCM, scrypt) into `backups\pre-upgrade`, with a generated passphrase held in `secrets.bin` and viewable by an administrator in About & Diagnostics, and **verifies it by restoring it into a throw-away database**. Only if verification passes are migrations applied. If the backup or any migration fails, normal start-up is blocked with the plain-language dialog, and nothing is dropped. The newest five safety backups are kept. A database that is _newer_ than the program (a downgrade) is refused.
8. **Single instance and ports.** A second launch asks the first to show its window and exits. Ports are chosen by the application, not fixed; a port that is taken is replaced, and the choice is recorded.
9. **Logging and diagnostics.** `app.log`, `postgres.log`, `api.log` under `logs\`, size-capped and rotated, with redaction. Settings, About & Diagnostics shows versions and runtime state and can save a diagnostics text file (no passwords, no business data, no file contents).
10. **The packaged service.** The API is bundled by esbuild into one `main.mjs` and run by the Electron binary as Node (`ELECTRON_RUN_AS_NODE`) so the user needs no Node. The `RunAsNode` fuse therefore stays enabled; it is mitigated by the existing launch secret, loopback-only binding and the control-secret channel (ADR-0006, ADR-0013). The native `argon2` module ships beside it (the packager skips `node_modules` in extraResources).
11. **Visual C++ runtime.** `vcruntime140.dll`, `vcruntime140_1.dll` and `msvcp140.dll` are copied app-local from the build computer's System32 into the PostgreSQL `bin` folder, so a laptop without the Redistributable still starts PostgreSQL. The Universal CRT is part of Windows 10/11.
12. **Unsigned now, signing-ready.** Without a certificate the build is an **UNSIGNED development/acceptance build** and the installer record says `signed: false`. If `WIN_CSC_LINK`/`WIN_CSC_KEY_PASSWORD` (or `CSC_*`) are supplied at build time, the installer and executables are signed. No certificate is created, faked or committed. Unsigned means Windows SmartScreen shows "Windows protected your PC" on the first run (R-108).
13. **Versioning.** `APP_VERSION` (SemVer, `0.1.0`) in `@commercebill/shared-types` equals the installer and `apps/desktop/package.json` version (a unit test enforces it). The schema version is the newest migration name. Document numbers and application versions are independent.
14. **The packaged end-to-end driver.** A packaged build accepts the end-to-end driver only if a marker file `resources\e2e-enabled` exists. `npm run package:win -- --e2e` adds it for the release tests; the release installer never contains it, so an installed program cannot run the driver (R-111).
15. **No binaries in git.** Installers, staging folders, databases, logs and backups are git-ignored; `release/installer-info.json` records name, version, SHA-256, size, command, signed flag and build environment.

## Consequences

- The installer is large (about 131 MB) because it carries PostgreSQL and Electron.
- There is no auto-update (R-112): a new version is installed over the old one by running the new installer; the pre-upgrade backup protects the data.
- A lost Windows profile loses the credentials; only a backup (kept off the computer) recovers the business (R-110, R-097).
- Native dialogs, a physical printer, an external drive and the target laptop are manual checks (R-093, R-105); the acceptance sheet lists them as NOT TESTED until someone performs them.
