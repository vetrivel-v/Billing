# ADR-0027: Encrypted backup format and verified recovery

- Status: Accepted and implemented in Phase 1 Task 1.17. R-031 is closed (superseded by the risks R-097 to R-103 below). R-040 stays open; passing tests does not enable production billing.
- Date: 2026-10-22
- Builds on: ADR-0009 (no `pg_dump` in the embedded PostgreSQL: a verified logical export), ADR-0010 (launch secret), ADR-0006 (Electron security baseline), ADR-0024 and ADR-0026 (immutable invoices and payments)

## Context

The embedded PostgreSQL ships no `pg_dump`/`pg_restore`. A raw copy of a running data directory is neither consistent nor portable. The production gate needs a fact, `BACKUP_RESTORE_VERIFIED`, that a boolean cannot honestly provide: it must come from evidence that a recent backup was actually restored somewhere and checked.

## Decisions

1. **Logical backup through the `pg` driver (ADR-0009, productionised).** One `REPEATABLE READ READ ONLY` transaction exports every application table as newline-delimited JSON. Concurrent writes are neither blocked nor included (the snapshot is the moment the transaction began). The `sessions` table is excluded: a restored database never inherits a signed-in session. Restore is "migrate, then load": the target gets the migration history of the backup's schema version applied in-process, and rows are loaded with `session_replication_role = 'replica'` (the superuser the embedded cluster already uses), then foreign keys and triggers are checked by the integrity checks, not trusted.
2. **One encrypted file per backup (`*.cbbackup`).** Header (`CBBACKUP`, format version, KDF id, scrypt `logN`/`r`/`p`, 16-byte random salt, 4-byte random nonce prefix, chunk size), then 1 MiB AES-256-GCM chunks (`length | ciphertext | 16-byte tag`). The nonce is `prefix || 64-bit chunk counter`; the associated data is the header plus a "final chunk" flag, so a wrong passphrase, any changed byte, a removed, reordered or appended chunk and a truncated file all fail authentication, and an empty or exact-multiple plaintext ends with an authenticated final chunk. The key is scrypt (`logN` 17, `r` 8, `p` 1) of a passphrase the user types and confirms (12 to 200 characters). A reader refuses parameters above `logN` 18, `r` 16, `p` 4, so a hostile file cannot demand unbounded memory or time. Salt and nonce are unique per backup: two backups of identical data share no header and no ciphertext.
3. **The passphrase is never kept.** It travels once in the request body over the loopback connection, is used to derive a key and is dropped. It is not stored, logged, audited, put in a URL, a manifest, the command line or an environment variable, and nothing can recover it. The screens and the guides say so plainly: lose it and the backup can never be opened.
4. **Container and manifest.** Inside the encryption: `manifest.json` and `data/<table>.ndjson`, as `name-length | name | size | bytes` records and an end marker. Only those two name forms are accepted; names are extracted to generated `entry-N.part` files, never to a path derived from the archive (path traversal is impossible by construction); entry count and size are capped; duplicates and trailing data are refused. The manifest (format, format version, backup id, kind `MANUAL` or `PRE_RESTORE`, creation time, application version, schema version, database identity, organization id and legal name, snapshot isolation, attachments `present: false`, excluded tables, per-table row count, byte count and SHA-256, encryption parameters without secrets) is validated strictly, and every data file must match its manifest checksum before anything is loaded. The manifest fingerprint (SHA-256 of its bytes) is stored in `backup_records`.
5. **Records, not booleans.** `backup_records` (one row per file made) and `backup_verifications` (one row per verification run, `PASS` or `FAIL`, engine version, schema version, database identity, check names and pass/fail only) are append-only. A record changes only to note, once, that retention removed its file. Both carry a monotonic `seq` used for every "latest" ordering, because timestamps can tie.
6. **VERIFIED means restored and checked.** Verification decrypts, validates the manifest and checksums, creates an isolated database (`cb_verify_<random>`), restores the backup into it, runs the integrity checks, re-exports the restored tables and compares them with the manifest checksums, records the result, and drops the isolated database. The checks are set-based SQL and report names and pass/fail only: schema version, business and administrator present, permissions present, all foreign keys, product references, protective triggers present (derived from the migrations, so a new trigger is automatically required), stock balances reconcile to the stock ledger (R-080: the projection is rebuilt from the ledger on restore and compared with the backup), tax configuration and review history, document sequences, invoice and payment numbers issued by the ledger, invoice totals equal their lines, dispatch links, payments fully allocated and within invoice totals, DEMO and production data kept apart, audit history present, and restored content identical. Any failed check records `FAIL`. A wrong passphrase or damaged file is reported but is not a verification result.
7. **The production gate reads the record.** `BACKUP_RESTORE_VERIFIED` is true only when the latest verification of the organization is `PASS`, was produced by the current verification engine, for the current schema version, for the current database identity, and is at most 30 days old. A later migration, a restore into a different database, a newer failed verification or the passing of time makes it false again. `AppDeps.backupRestoreVerified` remains an injectable test seam only; the real application never sets it. Verification does not switch anything on: switching to PRODUCTION is still a separate, explicit, reviewed step.
8. **Restore replaces the live database only after a safety backup and an explicit confirmation.** The administrator opens a backup (the same checks as verification, plus organization and schema compatibility) and types `RESTORE`. The service then enters maintenance mode (every request except `GET /health*` and `GET /backup/status` answers 503), creates and verifies a `PRE_RESTORE` backup of the current data, loads the chosen backup into a new database, runs the integrity checks, and only then swaps databases by renaming (the previous database is kept, renamed, never dropped). A failure at any step leaves the live database untouched. The restored database gets a new identity, so the production gate is false until a new backup is verified. The whole backup history, including the safety backup, is carried into the restored database. Sessions are not restored, so everyone signs in again (the screen goes straight to the sign-in page with an explanation). History entries whose author does not exist in the restored database (for example the administrator who is restoring, created after the backup) keep no author there: `created_by` and `verified_by` are optional, never a guess; carrying the history is best effort after the swap and reported as `historyCarried`.
9. **The renderer never touches the file system.** Choosing the backup folder and the restore file are IPC calls with no renderer argument: the main process checks the sender, opens the native dialog, and registers the chosen path with the local service over a second secret (`CONTROL_SECRET`, held only by the main process and the service, never sent to the renderer). The renderer receives only a display name and, for a restore file, an opaque id. The service accepts a folder only if it is an existing, writable directory, and a restore file only if it is a recognisable `.cbbackup` file; it never accepts a path from a client.
10. **One operation at a time.** Backup, verification, restore and retention take a session advisory lock on a dedicated connection; a second request while one runs answers 409 `busy`. The Electron backup flow is not scheduled and not automatic.
11. **Retention is conservative.** The administrator may keep the newest N verified backups. Only recognised `.cbbackup` files that the service itself recorded are ever removed; the most recent verified backup and any backup that never passed verification are never removed; a removal is recorded on the record.
12. **Permissions.** `backup.history.read` (Administrator, Accountant and Viewer/Auditor) reads status, history and readiness; `backup.create` and `backup.restore` are Administrator only. Organization scope always comes from the session. Audit rows (`backup.create`, `backup.create_failed`, `backup.verify`, `backup.retention_changed`, `backup.retention_applied`, `backup.restore_attempted`, `backup.restore_completed`, `backup.restore_failed`) carry facts only, never a passphrase, key or data.

## Alternatives rejected

- Copying the running data directory: inconsistent, not portable, not verifiable.
- A boolean setting "backup verified": the failure mode this ADR exists to prevent.
- Storing the passphrase to make backups easier: a stolen database would then reveal every backup, and a forgotten-passphrase recovery path would be a backdoor.
- Letting the renderer pass folder paths: gives a compromised renderer a file-system oracle.
- Restoring over the live database in place: a half-finished restore would destroy the only copy.

## Consequences

- A backup protects only if the file is kept somewhere other than this computer and the passphrase is kept separately (R-097, R-098). The product cannot enforce either.
- Verification restores into a separate database on the same machine: it proves the backup is readable and consistent, not that the backup survives a disk failure (R-097).
- A restore leaves the previous database on disk, renamed (R-099) and signs everyone out (R-100).
- Large databases take longer: the snapshot is streamed per table, but verification re-exports and re-checks everything (R-101).
- Attachments are not stored yet; the manifest records `present: false` and the format version will change when they are (R-102).
- Scheduled and automatic backups, cloud storage, point-in-time recovery and passphrase recovery are not built (R-103).
